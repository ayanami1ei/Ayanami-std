# 标准库设计标准

> 一句话：**对外声明式、对内过程式、整体面向对象。**
> 声明式是使用体验与优化抓手；过程式补齐声明式缺失的表达力；架构以类型为中心组织。

## 1. 声明式优先（Declarative first）

用户应当像「写声明」一样描述要做什么，而不是逐步命令式地做。两种主要手段：

### 1.1 标注系统（`#[...]`）

用标注把意图显式化：简化代码、给编译器/工具提供优化与检查依据。

| 标注 | 作用 | 现有例子 |
|---|---|---|
| `#[pure]` | 无副作用承诺（CSE/提升的基础） | `math` / `string` 的查询函数 |
| `#[alloc]` / `#[state]` | 分配 / 可变状态效应 | 集合方法、字符串构建 |
| `#[io]` | I/O 效应 | `print` / `println` / `getchar` |
| `#[noreturn]` | 发散（永不返回） | `panic_at` |
| `#[macro]` | 编译期源码变换（函数宏/标注宏） | `#assert*`、`#panic`、测试标注 |
| `#[pass]` / `#[check]` | MIR 优化 / 诊断插件 | `mir` 模块、注解式检查 |

原则：**能用标注表达意图的，不要留给读者猜**；标注必须与实现一致，否则优化会出错。

### 1.2 函数式风格

用接口、回调、构造器、宏，让用户几行完成一个完整步骤：

- 接口表达能力：`ToString`、`Into[T]`、`List[T]`、`Error`
- 回调/迭代：`a.iter((int x) { ... })`
- 构造器 + 方法链：`ArrayList::new[int]()`、`s.trim().parse_int()`
- 宏：`#assert_eq(...)`、`#panic(...)`

### 1.3 为什么声明式利于后期优化

声明（标注/接口/宏）把「意图」与「实现步骤」分离：
编译器与插件可以在声明层做变换（纯度提升、CSE、MIR 重写、检查注入），
而不必理解过程式细节；标准库升级优化时，用户代码无需改动。

## 2. 过程式是兜底（Procedural as escape hatch）

语言本身支持过程式编程，用来弥补声明式缺失的表达能力：

- 复杂控制流、性能敏感的内联循环、FFI/缓冲区边界，允许直接写过程式实现；
- **对外声明式，对内过程式**：公共 API 保持声明式用法，内部实现可以用最直接的循环/索引；
  例如 `read_line()` 对外是一行调用，内部可以是逐字符循环与缓冲构建；
- 过程式实现稳定后，可逐步抽成标注（`#[pure]` 等）或插件优化。

## 3. 面向对象架构（OO overall architecture）

- 数据与行为以**类型**为中心组织：`struct` + `impl` 方法 + `namespace` 构造器；
- 能力用**接口**（结构匹配）表达：`List[T]`、`ToString`、`Into[T]`、`Error`；
- 模块围绕类型/抽象划分（`String`、`ArrayList`、`LinkedList`、`Option`、`Result`、`Rng`…），
  避免散装函数集合；
- 运算符是 OO 的语法糖：`+`/`==`/`[]` 映射到 `add`/`eq`/`index`，行为与类型一致。

## 4. 写代码时的检查表

1. 新 API 能否用标注表达意图（纯度/分配/状态/IO/发散）？
2. 用户侧能否用「构造器 + 方法链 / 回调 / 宏」几行完成？能则不要暴露过程细节。
3. 性能/复杂度高的部分放内部过程式实现；对外签名保持声明式。
4. 新功能优先落到某个类型的方法/接口上；跨类型能力用接口约束。
5. 文档示例优先展示声明式用法；过程式写法放「进阶 / 实现」说明。

## 5. 演进方向

- 更多 `#[pass]` / `#[check]` 插件：纯度提升、边界检查优化提示、诊断注入；
- 更完整的声明式抽象：迭代器适配器（`map/filter/take/...`）、`Into` / `FromStr` 型接口；
- 保持 OO 组织：一个类型一个模块/章节，接口定义能力，标注表达意图。

## 6. 模块扩展准则（何时新增）

门槛：**实际需求驱动**——只有在下列场景之一出现时才扩展模块/API：

1. **实际项目**：程序无法用现有 API 合理表达的需求；
2. **教程示例**：官方示例/文档需要展示而缺失的能力；
3. **测试**：测试暴露的语义缺口（如错误信息不足、清理语义不可表达）。

流程要求：

1. 需求可复现（issue / 示例 / 测试用例）；不接受“以防万一”的 API；
2. 优先在既有模块内扩展（方法 / 接口 / 自由函数）；新模块要有清晰领域边界；
3. 新 API 必须带：`docs/modules/*.md` 说明 + 单元测试 + `SYMBOLS.md` 再生成（`test.sh` 门禁）+ 零告警；
4. 只有机器相关部分进 C 运行时（`runtime/`），其余纯 Ayanami 实现；
5. 与编译器能力的差距记录为 issue，不在 std 里做临时绕行（同 `docs/dev/plugins.md` 原则）。
